# Otis Phase 2 — Coding & Clustering Redesign (v1)
### Four scoped changes to make Pre-work output workshop-ready without new pipeline stages
*Builder doc for Claude Code. Amends: Phase 2 Coding Spec, clustering.ts, part2_coding.ts, workshop_seed shape (PreworkReview). Does NOT add a new pipeline stage; all four changes fit into existing files.*

---

## 0. Why this exists

Real-team output surfaced four related problems in the current Pre-work review:

1. **Anonymity risk.** Labels like "commenting that the member's house 'probably smells'" identify the person who said it. Handing this to a workshop is a psychological-safety violation.
2. **OUT vs. IN is undertheorized.** The coder assigns primary_code by the *source field* it was read from, not by whether the behaviour should be avoided or promoted. Many "OUT" labels are just "behaviours that happened."
3. **Absences masquerading as behaviours.** "Holding back," "not inviting," "withholding" cannot be practised. Teams can only practise their positive counterparts.
4. **Incident-anchored specificity.** "Not challenging the comment in the thread" is meaningless to a sorting member who doesn't know which thread. Every seeded behaviour is welded to a story.

Combined, these force the consultant to sanitise, abstract, and rewrite most seeded behaviours before releasing. That is not human-in-the-loop; that is human-does-everything.

**The redesign preserves the fidelity discipline at the evidence layer and adds workshop-readiness at the surface layer.** The consultant still has final say; nothing generated by the AI reaches a member without consultant review.

## 1. Change A — Anonymity guardrail at coding (new)

### What
Every coded label gets a new boolean `sensitive_specific`, set true when the label describes something only one person could plausibly have done, in a way that would identify them if the team read it.

### Signals the coder must check
Set `sensitive_specific: true` if ANY of:
- A named or clearly-implied role appears ("the manager," "the new hire," "the intern," "our lead")
- The label is a specific quote or near-quote of something said
- The label contains identifying content (culturally specific comments, physical descriptions, references to unusual personal details, specific incidents that only happened once)
- A team of 5 reading this label could reasonably guess who is being described

### Where it applies
`interview_labels.sensitive_specific: boolean, default false`. Coding prompt sets it per label.

### Downstream behaviour (locked)
- **Consultant Pre-work review:** `sensitive_specific: true` labels do NOT appear in the NEVER/ALWAYS circles by default. They live in a collapsed "Just for you — sensitive detail" drawer, visible only to the consultant.
- The consultant may promote a sensitive label to the workshop *only* after editing it into a de-identified generalisation. The raw sensitive form is never written to `workshop_seed.behaviours`.
- Clustering still runs on them (so counts are correct), but a cluster whose members are all `sensitive_specific` gets flagged `all_sensitive: true` and does not surface as a workshop candidate, only in the consultant's private view.

### Why this way
This is what D-046's multi-member flag was originally designed to catch, but the current implementation only flags dyadic vs. team-level, not identifiability. Identifiability is the sharper safety concern in a workshop context. Default-hidden is the right stance: for a psychological-safety tool, accidentally exposing a specific identifying comment is asymmetrically bad.

## 2. Change B — Recast primary_code as "avoid vs. promote," not "source field"

### The problem
Current coding prompt says: *"in_behavior FIELD often also names the bad behaviour it wants to replace. When a line in in_behavior_text describes an out-behavior, code it as primary_code 'out_behavior'."* This treats field-vs-code mismatch as a special exception. In practice, the reverse also happens constantly: members describe useful behaviours (something that did work, or a positive act) inside the out_behavior_text field, and the coder mislabels them OUT because they came from there.

### The rule
`primary_code` reflects the coder's judgment of whether the behaviour, on its own terms, is:
- `out_behavior`: something a team should **avoid** for psychological safety in this kind of situation, OR
- `in_behavior`: something a team should **promote** for psychological safety in this kind of situation.

The source field is preserved for audit (`source_field` stays as-is) but does NOT dictate the primary code.

### Test
For each labelled behaviour, ask: *"If a team adopted a norm that included this, would they be trying to reduce it (OUT) or increase it (IN)?"* That determines the code.

### Applied to your examples
- "asking to see a picture of the food" — code as IN (curiosity, engagement — something you'd want more of)
- "commenting that the member's house probably smells" — code as OUT (identifying + inappropriate — something you'd want none of)
- "standing up and calling out the comment" — code as IN (constructive intervention)
- "handing the completed protocol to their boss" — code as OUT *only if* the label is framed as bypassing peers; if it's framed neutrally, do not code (see Change C on absences and Change D on the higher-abstraction form).

## 3. Change C — Absences are reframed at coding time (not emitted as-is)

### The rule
**Never emit a label whose head verb describes an absence.** No "not X," no "holding back from Y," no "withholding Z," no "failing to A."

### What to do instead
When the interview describes an absence, the coder must decide which of two things it actually is, and emit accordingly:

1. **The absence points to something that DID happen** — a specific act took place that had the effect of excluding, silencing, or hiding. Code the *positive act* that happened, as OUT.
   *Example:* "nobody asked me for feedback" → what happened is: proceeding without consulting. Emit `"proceeding without consulting others"` as OUT.

2. **The absence points to something that SHOULD have happened but didn't** — no specific act took place; the interview is really about a missing positive. Emit the *positive that should have been present*, as IN.
   *Example:* "I felt like I was holding back from reaching out for help" → what should have happened is: reaching out. Emit `"reaching out for help early"` as IN.

If both apply, emit both.

### Why
Teams cannot practise "not doing X." They can only practise doing Y instead. Behavioural agreements built on absences don't hold. This change removes the entire "avoidance-shaped" label category from the pipeline.

### Applied to your examples
- "holding back from reaching out to the engineer" → `"reaching out for help early"` (IN)
- "not inviting broader input or improvement ideas" → `"inviting input before decisions"` (IN) OR `"proceeding without asking for input"` (OUT), depending on which the interview text actually describes
- "never acknowledging the member's work" → `"acknowledging contributions"` (IN) OR `"skipping over someone's contribution"` (OUT), same rule

## 4. Change D — Add `workshop_form` to each cluster (the ChatGPT insight, applied with the guardrail)

### What
The clustering step's LLM naming call (already exists in `clustering.ts` → `nameClusters`) is expanded to produce **two** outputs per cluster, not one:

- `name` (existing): a short canonical grouping label, 2–5 words, close to members' words. Used on the consultant dashboard for counting/ranking. *Unchanged.*
- `workshop_form` (new): a short, transferable behavioural phrase — a behaviour a team could realistically adopt or avoid across many future situations, not tied to the specific incidents in the cluster.

### Where `workshop_form` is used
- **In the Pre-work review's NEVER/ALWAYS circles.** These now show the `workshop_form` by default, with the source labels behind a one-click expander ("see the specific incidents behind this").
- **Written to `workshop_seed.behaviours[].text` on release**, so the member sort screens show workshop-ready behaviours, not incidents.
- The `name` still appears on the consultant dashboard's cluster boxes (unchanged).

### Rules for `workshop_form`
1. Must be a **transferable behaviour**, not the specific incident. Test: could this behaviour apply to at least three different situations the team hasn't discussed?
2. Must be a **positive-form behaviour** even for NEVER clusters. Absences are still forbidden here (Change C's rule extends to cluster naming). A NEVER cluster's `workshop_form` is still an action, one the team commits NOT to do.
   *Example:* NEVER cluster of "cutting people off," "talking over," "interrupting" → `workshop_form: "talking over others in group discussions"` (a concrete action the team commits not to do), NOT `"not interrupting"` (an absence).
3. Must be **de-identifiable**. If the raw source labels contain identifiable specifics, the `workshop_form` must strip them. Roles, quotes, cultural specifics all get abstracted.
4. Must stay **close to members' vocabulary**, not consultant jargon. "Talking over each other" beats "practising conversational turn-taking."
5. Must be **something someone could see or hear**, per the observability rule that already governs coding.

### What if the cluster is all `sensitive_specific`?
Set `all_sensitive: true` on the cluster and DO NOT surface it to the workshop. It appears only in the consultant's private view with a note explaining why.

### Why this doesn't reopen the "AI shouldn't unilaterally abstract" concern
Because the consultant reviews it in Pre-work before anything reaches a member. The AI proposes a workshop-ready form; the human accepts, edits, or rejects it. Fidelity is preserved at the evidence layer (source labels unchanged); workshop-readiness is added at the surface layer.

## 5. Concrete changes per file

### `prompts/part2_coding.ts` (Change A, B, C)
Add three sections to the system prompt:

**A — Anonymity flag.** New "sensitive_specific" section describing the four signals and instructing the coder to set the flag per label.

**B — Avoid/promote determines primary_code.** Rewrite the existing "IMPORTANT: the in_behavior FIELD often also names the bad behavior it wants to replace" paragraph into a general rule: primary_code is determined by whether the behaviour should be avoided or promoted, not by the source field. Include the test ("If a team adopted a norm including this, would they reduce it or increase it?").

**C — No absences.** Add "Absences are not behaviours" section with the two-branch decision (what happened → code the act as OUT; what should have happened → code the positive as IN) and the forbidden vocabulary list (no head verb of "not X," "failing to," "holding back," "withholding," etc.).

Update the tool schema `record_labels` to include `sensitive_specific: boolean`.

### `lib/coding.ts` (Change A schema plumbing)
- Add `sensitive_specific` to `RawLabel`, `toInsert` (default false, coerce to boolean).
- Add `sensitive_specific` to `InterviewLabelInsert` in `types/database.ts`.
- Migration: `alter table interview_labels add column sensitive_specific boolean not null default false;`

### `lib/clustering.ts` (Change D)
Modify `NAME_CLUSTERS_TOOL` and `nameClusters`:
- Tool schema returns `{ names: string[], workshop_forms: string[] }` (parallel arrays, same order).
- System prompt for naming is expanded to explain what `workshop_form` is and the five rules for it, plus the absence-forbidden rule.
- The `Cluster` type gets `workshop_form: string` and `all_sensitive: boolean` fields.
- After `buildClusters`, set `all_sensitive = source_labels.every(l => l.sensitive_specific)` (this requires exposing `sensitive_specific` on `SourceLabel`).

### `lib/preworkSeed.ts` and `PreworkReview.tsx` (Change D + A surface)
- Seeded behaviours in `workshop_seed.behaviours` now default to `cluster.workshop_form`, with `source_labels` still stored for the expander.
- The NEVER/ALWAYS circle UI shows `workshop_form` text by default; an expander reveals source labels.
- `all_sensitive` clusters are excluded from the primary behaviour list.
- A new "Just for you — sensitive detail" drawer, collapsed by default, contains `sensitive_specific` individual labels and `all_sensitive` clusters, with a note that they should not be surfaced to the workshop without de-identification.
- The consultant can promote from the drawer by editing (creating a de-identified version), which then appears as a normal behaviour with provenance `consultant`.

### Migration for `interview_labels` and `workshop_seed`
```sql
alter table public.interview_labels
  add column sensitive_specific boolean not null default false;
-- workshop_seed.behaviours is jsonb; each entry now optionally carries:
-- { workshop_form: string, source_labels: SourceLabel[], all_sensitive?: boolean }
-- no schema change needed for jsonb; app-level typing only.
```
Same RLS-disable pattern as prior migrations (drop policies loop → alter table disable RLS).

## 7. Testing checklist for Claude Code

After implementing, re-run analysis for team "test" and verify:
1. No label in `interview_labels` has a head verb of "not X," "holding back," "withholding," "failing to," "never X-ing."
2. The "house smells" label (and similar identifiable comments) have `sensitive_specific: true`.
3. At least some labels have `primary_code` that disagrees with `source_field` (proves Change B is active).
4. Each cluster has a `workshop_form` that reads as a transferable behaviour a team could adopt.
5. The Pre-work review's NEVER/ALWAYS circles show `workshop_form`s, not raw incidents.
6. The "Just for you — sensitive detail" drawer exists and contains at least one item (the "house smells" material).
7. No `workshop_form` mentions a specific role, quote, or cultural identifier.
